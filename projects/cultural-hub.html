CulturalHub

Bachelor's thesis — a web platform for discovering, booking and managing cultural events across Romania.

Laravel 12 PHP 8.3 MySQL Blade Tailwind CSS Alpine.js Stripe PHPUnit

Overview

CulturalHub is my bachelor's thesis project, supervised at Lucian Blaga University of Sibiu. Visitors browse and filter theatre, opera, cinema and concert events, pick their own seats on a rendered hall map, and pay online. Organizers publish and manage their own events; administrators have full control over users, categories, venues and reporting.

The goal was not another ticket shop but a platform that takes the administration side seriously — the part most existing services hide from the people actually running events. It also grew beyond a single application: the same domain is now covered by a native Android client and a Python recommendation engine.

Features

  • Visual seat selection — hall maps rendered from a JSON layout, distinguishing standard, premium and accessible seats, with the total updating as seats are picked.
  • Three-role access control — user, organizer and admin, enforced by a single middleware across every route.
  • Online payments — Stripe integration with webhook confirmation, plus a mock provider for local development and tests.
  • Event management — full CRUD with image upload, pricing, categories, venues and draft/published/cancelled states.
  • Reporting and export — statistics dashboard with export to CSV, Excel and Google Sheets.
  • Email notifications — welcome, reservation and payment confirmations, dispatched through a queue so they never block the response.

Payments: the Strategy pattern

The application never talks to Stripe directly. Everything goes through the IPaymentProvider interface, which defines three operations: create a checkout session, validate a webhook event, and identify the provider.

PaymentService ↓ (depends only on the interface) IPaymentProvider ├── StripeProvider # real Stripe API └── MockPaymentProvider # simulated, used in tests

Which implementation is used is decided at runtime from a config variable, through Laravel's dependency injection. The practical payoff: the whole payment flow can be tested without a network connection, and swapping providers would not touch a line of business logic.

Reservation integrity

Creating a reservation runs inside a database transaction. Each selected seat is checked individually; if any one has already been taken, the whole operation rolls back rather than leaving a half-written booking. Valid seats are stored as separate rows in reservation_seats, so availability is a property of the data rather than something the application has to remember.

Paid events stay in pending until the payment provider's webhook arrives — the webhook is the source of truth, not the browser redirect, which a user can close or refresh. The handler is idempotent, so a webhook delivered twice is processed once.

Architecture

Request ↓ Routes & Middleware # authentication, role checks ↓ Controllers # Event, Reservation, Payment, Admin, Raport ↓ Services # PaymentService, ReportService ↓ Eloquent Models → MySQL ↓ Blade Views # Tailwind CSS + Alpine.js

Business logic lives in services rather than controllers, which stay thin: receive, validate, delegate. Authorization sits in one middleware instead of scattered conditionals, so it applies uniformly.

Testing

50 automated tests, 146 assertions, running in about eight seconds against an isolated test database. They cover the reservation flow including its failure cases (seat count mismatch, already-taken seat), the full payment cycle from checkout to webhook, webhook idempotency, role-based access, and email dispatch.

What I learned

Two things stand out. First, modelling seats as individual rows rather than a count made the concurrency problem disappear — the schema enforces what would otherwise be fragile application checks. Second, hiding the payment provider behind an interface was worth the extra indirection the first time I ran the whole payment suite offline in under a second.
